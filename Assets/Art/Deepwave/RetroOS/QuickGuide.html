Summary

Retro OS is a data-driven Windows 95-style operating system you drop into any Unity game: desktop, draggable windows, Start menu, login screen, a virtual file system, a working terminal, mail, CCTV monitors, a retro web browser and a synthesized-sound audio module. Every program is a component you add to the machine, its drives are folders you can drop a text file into, and every interaction raises a game event so rules, UnityEvents or code can turn OS actions into story beats.

Description _▢✕

Retro OS turns a Canvas into a working Windows 95-style desktop: draggable, resizable windows with real chrome, a Start menu, a taskbar with live window buttons and a clock, desktop icons that snap to a grid, and a login screen gating access. Everything on screen — buttons, bevels, scroll bars, even the 71 program icons — is built procedurally in code, so the package ships with essentially zero image or audio assets and still looks and sounds authentically 90s.

A computer is authored on the computer: RetroMachine carries its name, its user accounts and the BIOS screen it prints on the way up, while the RetroOsBootstrap beside it carries the system installed on it — its name, wallpaper, sounds and a list of no-code Rules that react to what the player does. The date, the data folder and the LAN belong to the scene's RetroWorld, because the computers in a room are in the same room. Its file system is real folders on disk. Programs are components — add them to children of the bootstrap (Add Component, then search for the one you want by name), subclass RetroAppBehaviour for a code-built one, or use the no-code RetroPrefabApp to wire up your own uGUI prefab. Installing a program is adding the component.

How It Works

A RetroOsBootstrap component is the whole composition root: it builds the canvas and services from the machine it sits on, installs the programs under it, and boots to the login screen (or straight to the desktop if no users are configured). From there the player drives everything, and the OS reports back through one event bus.

1

Author the computer

Users on the machine; wallpaper, sounds & story rules on the OS

2

Bootstrap Boots

Builds the canvas & services, shows login or the desktop

3

Player Interacts

Opens apps, runs commands, reads mail, browses CCTV / the web

4

OS Raises Events

Every action fires an event id + argument on the shared bus

5

Your Story Reacts

Rules, a UnityEvent listener, or code turn events into gameplay

Why this matters: because reactions are decoupled from the OS itself, the same file-open or camera-select event can unlock a door, deliver a threatening email, play a sound, or set a story flag — all without touching a single line of Retro OS's own code.

Getting Started

The fastest path to a running OS is the setup window; a from-scratch machine takes a few more minutes.

  1. Add the bootstrap

    Add an empty GameObject, then add RetroOsBootstrap to it.

  2. Add the computer

    Run Deepwave → RetroOS → Setup, or add a RetroOsBootstrap to an empty GameObject by hand — its RetroMachine comes with it.

  3. Install programs

    Add the programs you want as components on children of the bootstrap (Add Component, then search for each one by name), or tick them in Deepwave → RetroOS → Setup and let it build the object for you. File viewers (Notepad, Image Viewer, Media Player, CD Player) work automatically even if you install nothing else.

  4. Author content

    Add users on the machine and a wallpaper on the OS, and drop files into the machine's folder under StreamingAssets/RetroOS. Per-program content lives on the program's own component — camera channels on CCTV, messages on the Inbox, pages and bookmarks on the browser, contacts on the Messenger.

  5. Wire up story reactions

    Add no-code Rules on the bootstrap, and/or drop a RetroOS Event Listener on any scene object and wire UnityEvents to OS events.

  6. Press Play

    The sample content logs in with operator / 1997.

  7. Optional: put it on a 3D monitor

    Assign a RenderTexture asset to the RetroMonitor's Texture Asset and drop the same asset into your screen material, then add First Person Controller + Retro Workstation to walk up, press E to focus the screen, and Space/Esc to step back.

See it end-to-end: the bundled RetroOsDemo sample scene is a full 3D room with two working computers and a small mystery wired entirely through Rules — a good reference for how the pieces fit together.

Core Concepts

A closer look at each system, grounded in what the shipped scripts actually implement.

The Computer & Installing Apps

A computer is two components on one object: RetroMachine holds its Users and its start-up screen, RetroOsBootstrap holds the Wallpaper, Sounds and story Rules of the system on it, and the scene's RetroWorld holds the in-fiction System Date. Its drives are real folders on disk, and its programs are components under it. Nothing is hard-coded — a machine with no users configured boots straight past the login screen to the desktop.

Each program is a component deriving from RetroAppBehaviour, carrying an App Id (stable id for events and rules), Title, icon (custom sprite or one of 71 built-in pixel icons), window size/min-size/resizable/start-maximized, Single Instance (re-focus instead of opening twice), a Start-menu Category, and desktop/Start-menu placement flags. Installing a program is adding the component to a child of the bootstrap.

Two ways to build one: subclass RetroAppBehaviour and override BuildContent(AppContext) for a fully code-built program (a handful of lines using the RetroUi widget factory), or add the built-in Prefab App component and point it at your own uGUI prefab — any component on it implementing IRetroAppView receives the app context automatically, no RetroOS code required.

Virtual File System & Discs

The file system is the real folders inside the machine's own folder on disk, and each node can be Hidden (omitted from listings unless explicitly shown) and independently Encrypted with a password.

There is no file list to author. A machine's drives are the folders inside its folder under StreamingAssets/RetroOS/machines: a folder named C is the C: drive, A and B are floppies, everything else is a hard disk. A file's extension decides which viewer opens it, and content loads lazily, so a thousand documents cost nothing until one is opened. Anything the OS needs beyond that — hidden, encrypted, a password, a disc label, an owner — goes in a <name>.rmeta sidecar you can edit in the Inspector. An empty floppy or CD folder is a drive with no disc in it, and says so.

Encryption is narrative, not real security: a locked node just asks for a password before it opens — the bytes on disk stay the plain file, readable in any text editor. It is meant to gate story content, not to protect actual sensitive data. Unlock via the in-app password prompt, the terminal's decrypt <path> <password>, or a rule's UnlockNode action.
Windows, Desktop & Taskbar

Every open app gets real Win95 window chrome: a title bar with icon, minimize/maximize/close buttons, an optional resize grip with the classic dotted-triangle glyph, and cascading placement so new windows never stack exactly on top of each other. Windows are always clamped to the desktop's work area — they can never be dragged or resized off-screen or behind the taskbar.

The desktop lays out icons top-to-bottom in columns for every app with Show On Desktop enabled; dragging an icon snaps it to a grid on release, and dropping it on an occupied cell bumps it to the nearest free one instead of stacking. The taskbar shows a live button per open window (click to focus/minimize) plus a clock tray that ticks on the in-fiction system clock, not real time.

The Start menu stays compact no matter how many apps are installed: programs live behind a scrolling Programs fly-out rather than a flat list, with an Insert Disc fly-out alongside it when the machine has a removable drive, and Log Off / Shut Down entries at the bottom.

CCTV: Live Cameras & DVR Playback

Each CCTV channel can combine, in priority order: a live device (a CctvCameraDevice placed on a real scene Camera, matched by a shared Device Id — it only renders while actually being watched), a recorded tape (a VideoClip reviewable in PLAYBACK), and/or a still image shown when nothing else is available. A channel with nothing configured shows NO SIGNAL static.

Toggle between LIVE and PLAYBACK per channel. Live mode pans/zooms the real scene camera (rotation + field of view, clamped to configured ranges); recorded or buffered playback instead pans/zooms digitally over the image. With Allow DVR enabled, a live channel silently buffers roughly 8 seconds of its own feed, so PLAYBACK can rewind and scrub it with a transport bar even when no VideoClip was ever authored.

The monitor itself sells the era: scanline overlay, procedural static noise, a blinking REC dot while live, and an in-fiction timestamp. Selecting a channel raises cctv.selected — a natural trigger for a horror beat.

Web Browser & RetroML

Pages are authored per-site on the web browser app's own Sites list, keyed by URL, and written in a tiny line-based markup called RetroML:

SyntaxRenders as
# Heading / ## SubheadingBold heading text, two sizes
---A sunken horizontal divider
[img:id] / [img:id:height]An image block; multi-frame images animate as a flipbook
[link:url:Caption]A clickable link that navigates the browser
anything elseA paragraph — Unity rich text (<b>, <i>, <color=#RRGGBB>) is allowed

The browser keeps a real Back/Forward history (a new navigation discards any forward entries, exactly like a real browser), and raises web.visited on every page load. An unknown URL shows an in-fiction "page cannot be displayed" error instead of breaking.

Game Events & Story Rules

Everything the OS does raises an event on a shared bus: os.boot, os.login/os.logout, os.shutdown/os.poweron, os.bsod, app.opened/app.closed/app.focused/app.minimized/app.maximized/app.action, file.opened/file.saved/file.denied, node.unlocked/node.revealed, fs.changed, explorer.navigated, terminal.command, mail.received/mail.read/mail.sent/mail.deleted, reminder.due, printer.job, chat.message/chat.said, web.visited/web.failed/web.download, cctv.selected, disc.inserted/disc.ejected, net.mounted/net.reached/net.unreachable, and flag.set/flag.cleared — 39 in total, each carrying an optional string argument.

Three ways to react, from no-code to full code:

  1. Story Rules — no code at all: match an event id (+ optional argument, trailing * for a prefix match, + an optional story-flag gate) and run one or more actions.
  2. RetroOS Event Listener — drop this component on any scene object and wire UnityEvents in the Inspector to specific events (or to every event via a catch-all).
  3. Code — subscribe directly: RetroOs.Current.Events.Subscribe("file.opened", path => ...), check story state with Flags.IsSet(...), or raise your own custom events with RetroOs.Raise(...).
SetFlag / ClearFlag RevealNode / HideNode UnlockNode DeliverMail OpenApp ShowAlert Notify PlaySound RaiseEvent Bsod LogOff / Shutdown HostOnline / HostOffline ChatOnline / ChatOffline

Those 18 rule actions are enough to build a self-contained mystery entirely from data: reveal a hidden file once a flag is set, unlock an archive, deliver a threatening email a beat later, take a web site off the air, raise a blue screen, or chain into a completely custom event of your own.

Audio & 3D World-Screen Rendering

Nine interaction sounds (click, window open/close, error, startup fanfare, login, notify, disc insert/eject) are configured on the bootstrap with optional clip overrides; any empty slot falls back to a tone synthesized at runtime from sine and square waves, so the OS makes period-correct noise with zero audio assets. A separate one-track music channel (used by the CD Player) plays independently of the UI sounds.

The interface is drawn once, flat, by a projector camera that sees nothing else, into a RenderTexture — and that texture is the machine's picture. Assign that asset to the RetroMonitor's Texture Asset and drop the same asset into the CRT's glass material, and it appears there, glowing convincingly across a dim room — the OS never touches your materials, so any shader and any number of surfaces work. When the player sits down at it, SetFocused(true) flips the canvas to a screen-space overlay and switches the projector off, so the OS is pixel-exact at the display's own resolution while it is in use rather than resampled at whatever angle the scene camera happens to see it from. An on-screen cursor mode instead keeps the OS on the glass and walks a drawn pointer across it with the mouse, a gamepad stick or a dragging finger. The work area can still be inset to a normalized rect or letterboxed to a fixed aspect like 4:3. The bundled First Person Controller + Retro Workstation components handle the walk-up, press-E-to-focus, Space/Esc-to-leave interaction loop used by the demo.

Help — Frequently Asked Questions _▢✕
Do I need to write code to add a new program to the OS?

No. Add the no-code Prefab App component and point it at a uGUI prefab — components on it implementing IRetroAppView receive the app context automatically — or subclass RetroAppBehaviour and override BuildContent for a code-built program. Either way the program is a component on a child of the bootstrap, and installing it is adding it.

Can actions inside the OS affect my game outside it?

Yes. Every OS action raises an event (file opened, mail read, terminal command, CCTV camera selected, and more). React with no-code Rules on the machine's bootstrap, a UnityEvent-based RetroOsEventListener component, or a direct C# subscription.

Does Retro OS need any audio assets to make sound?

No. All 9 interaction sounds are synthesized at runtime from sine and square waves. You can still assign your own AudioClip per sound to override the synthesized tone.

Can the OS run on a 3D monitor inside the game world?

Yes. The OS is drawn once into a RenderTexture; assign that asset to the RetroMonitor's Texture Asset and drop the same asset into your screen material, and it appears on the glass, always lit. When the player sits down at it the canvas flips to a screen-space overlay so it is pixel-exact while it is in use — or an on-screen cursor mode keeps it on the glass and walks a drawn pointer across it. A First Person Controller plus Retro Workstation component pair drives a walk-up-and-use flow.

Does CCTV need pre-recorded footage to support rewind?

No — enable Allow DVR on a live channel and it automatically buffers roughly 8 seconds of the feed, which PLAYBACK mode can rewind and scrub even with zero pre-authored video clips.

Can I lock files behind a password?

Yes. Mark a file or folder Encrypted with a password; it unlocks via a UI prompt, the terminal's decrypt command, or a rule's UnlockNode action. The bytes on disk stay plain — the flag just gates opening behind a password prompt. It is narrative gating, not real security.

What Unity version and dependencies does Retro OS need?

Unity 2022.3 or newer. It ships with no external package dependencies and is built entirely on Unity's standard uGUI and Input System.

Can mail arrive later in the story instead of at boot?

Yes. Mark a message Delayed on the Inbox app's mail list and it stays invisible until a rule's DeliverMail action (or the equivalent code call) sends it — the inbox updates live while the player is inside it.
